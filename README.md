# state-forecaster

Author: Gary Black <br>
Last updated: August 6, 2026

## Purpose

The state-forecaster directory of the state-forecaster repository contains the entirety of the FY26 GridAPPS-D application deliverable that uses state estimates to forecast future state. The prototype directory contains the developmental code that evolved into the full application and now serves as a reference for the application design and implementation. Note there are several versions of the prototype summary in that directory that are useful in seeing the evolution of the design and code.

## Overview

The detailed design of the State Forecaster application can be found at <https://github.com/GRIDAPPSD/state-forecaster/blob/main/state-forecaster/app_summary_v7.md>. AI was used in the design and coding of this application, specifically Anthropic Claude Opus 4.8, with ongoing and continual interaction by Gary Black at PNNL as the developer. The application summary linked above was generated by AI from the chat history for the development of the application. The original algorithm code that validated the deep neural network approach implemented in the application was written by Avijit Das at PNNL. Through many stages of development this initial code first evolved into the prototype and finally the full State Forecaster application.

The State Forecaster is dependent upon the GridAPPS-D State Estimator application to supply the state estimates that train the neural network and predict future state. The State Estimator takes in GridLAB-D simulation measurements or Sensor Simulator service output to produce state estimates. Thus, the full workflow for State Forecaster consists of a GridAPPS-D platform instance running a GridLAB-D simulation, either with or without the Sensor Simulator service running under the GridAPPS-D platform, the State Estimator application receiving simulation or sensor measurements, and the State Forecaster application receiving state estimates to produce forecasts.

Communication between services and applications uses the publish/subscribe model and is done over the GridAPPS-D message bus including published forecasts as the final output. While the normal workflow includes the GridAPPS-D platform, a live GridLAB-D simulation and State Estimator instance, file-based input to the State Forecaster outside the GridAPPS-D platform is also supported for testing purposes. In this case the same JSON structure based state estimates that are published by State Estimator are instead read from a file that was previously generated by the State Estimator.

## Prerequisites

As of August 6, 2026, the State Forecaster runs with the "develop" GridAPPS-D platform release.

You must have the dockerized GridAPPS-D platform running which is available at https://github.com/GRIDAPPSD/gridappsd-docker. Follow the documentation there if you are unfamiliar with running the platform. To run the run.sh script you may first need to do a "sudo apt install docker-compose" and "sudo rm /usr/local/bin/docker-compose". To run the "develop" platform release, use "./run.sh -nt develop" followed by "./run-gridappsd.sh" in the docker container shell.

The gridappsd-python package must be installed in Python. To check if this package is already installed:

```` bash
$ python
>>> import gridappsd
````

If the import returns an error message, see <https://github.com/GRIDAPPSD/gridappsd-python> for installation instructions. You may need to do a "sudo apt install python-pip" to be able to do the "sudo pip install gridappsd-python" needed to install this package.

Various other Python packages are required to run State Forecaster and can be installed with "sudo pip install <package>" if not already installed (check with import statements in the Python command-line interpreter). These packages include numpy and torch.

## Running State Forecaster

A three-terminal strategy for running State Forecaster is recommended. The GridAPPS-D platform in run in the first terminal through the "./run-gridappsd.sh" command, State Estimator in the second terminal, and State Forecaster in the third terminal.

Note that the GridAPPS-D platform currently contains only a 1-day load profile schedule named ieeezipload. State Forecaster (non-real-time) simulations typically run 14 days or longer to generate the 2-day blocks of state estimates used for neural network training. Thus it may be necessary to import longer schedules into the influx database that runs under the influxdb container of the GridAPPS-D platform. The gridappsd-data repository has basic instructions for generating the input .txt file for the influx import command from .player files, although based on the length of the schedule the Python utility script that converts .player to .txt files will need to be updated as it repeats data to generate a full years' data. Once the .txt file is generated it is copied to the influxdb container with a command such as "docker cp loadprofile_measurement_out_1year.txt influxdb:/tmp". Then a docker shell is created for the influxdb container with "docker exec -it influxdb /bin/bash". Then cd to /tmp in that shell and the command to import the schedule is "influx -import -path=loadprofile_measurement_out_1year.txt -precision s". The JSON simulation config file is then able to reference this new schedule in the "schedule_name" attribute.

In the second terminal from the state-estimator directory under the gridappsd-state-estimator repository (see the README.md file at the top-level of that repo for instructions on building and running the C++-based State Estimator), use the "run-se.sh" wrapper script to start a GridLAB-D simulation and invoke the State Estimator tied to this simulation. For example, "./run-se.sh 13latest" would use the 13latest-config.json file in the sim_starter directory to start a simulation for the 13nodecktassets model and then invoke State Estimator on this simulation. Note that the simulation ID is printed to the terminal in the first few lines of output from "run-se.sh" and this should be copied as it will be needed for running State Forecaster.

In the third terminal from the state-forecaster directory under the state-forecaster repository, create a "logs" directory if one does not already exist. Then run "./state_forecaster \<simid\>" where \<simid\> is the simulation ID printed in the second terminal where the simulation and State Estimator were started. The main state_forecaster.py module spawns three subprocesses (that use Python multiprocessing support to communicate amongst themselves) and the log output for these is intermixed to the terminal where state_forecaster.py was invoked. The logs subdirectory contains separate log files for each of the three spawned subprocesses and you may wish to do "tail -f" commands for these in other terminals during the run. When State Estimator finishes producing estimates for a simulation it sends a COMPLETE processStatus message that State Forecaster receives to exit cleanly after completing any remaining processing.
