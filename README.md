# state-forecaster

Author: Gary Black <br>
Last updated: August 14, 2026

## Purpose

The state-forecaster directory of the state-forecaster repository contains the entirety of the FY26 GridAPPS-D application deliverable that uses state estimates to forecast future state. The prototype directory contains developmental code that evolved into the full application and now serves as a reference for the application design and implementation (the prototype is not needed to run the application). Note there are several versions of the prototype summary in that directory that are useful in seeing the evolution of the design and code.

## Overview

The detailed design of the State Forecaster application can be found at <https://github.com/GRIDAPPSD/state-forecaster/blob/main/state-forecaster/app_summary_v7.md>. AI was used in the design and coding of this application, specifically Anthropic Claude Opus 4.8, with ongoing and continual interaction by Gary Black at PNNL as the developer. The application summary linked above was generated by AI from the chat history for the development of the application. The original algorithm code that validated the deep neural network approach implemented in the application was written by Avijit Das at PNNL. Through many stages of development this initial code first evolved into the prototype and finally the full State Forecaster application.

The State Forecaster is dependent upon the GridAPPS-D State Estimator application to supply the state estimates that train the neural network and predict future state. The State Estimator takes in GridLAB-D simulation measurements or Sensor Simulator service output to produce state estimates. Thus, the full workflow for State Forecaster consists of a GridAPPS-D platform instance running a GridLAB-D simulation, either with or without the Sensor Simulator service running under the GridAPPS-D platform, the State Estimator application receiving simulation or sensor measurements, and the State Forecaster application receiving state estimates to produce forecasts.

Communication between services and applications uses the publish/subscribe model and is done over the GridAPPS-D message bus including published forecasts as the final output. While the normal workflow includes the GridAPPS-D platform, a live GridLAB-D simulation and State Estimator instance, file-based input to the State Forecaster outside the GridAPPS-D platform is also supported for testing purposes. In this case the same JSON structure based state estimates that are published by State Estimator are instead read from a file that was previously generated by the State Estimator.

State Forecaster was deliberately designed to be as minimally coupled to the GridAPPS-D platform as possible. For messaging it only relies on the State Estimator and does not subscribe to other services including simulation output or log messages. Further, it does not query the network model such as for bus, node, mrid, or device information. The necessary information is derived from the published state estimates.

## Prerequisites

As of August 6, 2026, the State Forecaster runs with the "develop" GridAPPS-D platform release.

You must have the dockerized GridAPPS-D platform running which is available at https://github.com/GRIDAPPSD/gridappsd-docker. Follow the documentation there if you are unfamiliar with running the platform. To run the run.sh script you may first need to do a "sudo apt install docker-compose" and "sudo rm /usr/local/bin/docker-compose". To run the "develop" platform release, use "./run.sh -nt develop" followed by "./run-gridappsd.sh" in the docker container shell.

The gridappsd-python package must be installed in Python. To check if this package is already installed:

```` bash
$ python
>>> import gridappsd
````

If the import returns an error message, see <https://github.com/GRIDAPPSD/gridappsd-python> for installation instructions. You may need to do a "sudo apt install python-pip" to be able to do the "sudo pip install gridappsd-python" needed to install this package.

Various other Python packages are required to run State Forecaster and can be installed with "sudo pip install <package>" if not already installed (check with import statements in the Python command-line interpreter). These packages include numpy and torch. Start by installing these two packages if you don't have them and then try running the app to see if it calls out any others on failed imports.

## Running State Forecaster

A three-terminal strategy for running State Forecaster is recommended. The GridAPPS-D platform in run in the first terminal through the "./run-gridappsd.sh" command, State Estimator in the second terminal, and State Forecaster in the third terminal.

Note that the GridAPPS-D platform currently contains only a 1-day load profile schedule named ieeezipload. State Forecaster (non-real-time) simulations typically run 14 days or longer to generate the 2-day blocks of state estimates used for neural network training. Thus it may be necessary to import longer schedules into the influx database that runs under the influxdb container of the GridAPPS-D platform. The gridappsd-data repository has basic instructions for generating the input .txt file for the influx import command from .player files, although based on the length of the schedule the Python utility script that converts .player to .txt files will need to be updated as it repeats data to generate a full years' data. Once the .txt file is generated it is copied to the influxdb container with a command such as "docker cp loadprofile_measurement_out_yearly.txt influxdb:/tmp". Then a docker shell is created for the influxdb container with "docker exec -it influxdb /bin/bash". Then cd to /tmp in that shell and the command to import the schedule is "influx -import -path=loadprofile_measurement_out_yearly.txt -precision s". The JSON simulation config file is then able to reference this new schedule in the "schedule_name" attribute. Note that a 1-year simulation load profile schedule ready for influx import has been placed in the state-estimator/sim_starter directory of the gridappsd-state-estimator repo named loadprofile_measurement_out_yearly.txt as a convenience (no need to clone the gridappsd-data repo unless new schedules will be generated).

In the second terminal from the state-estimator directory under the gridappsd-state-estimator repository (see the README.md file at the top-level of that repo for instructions on building and running the C++-based State Estimator), use the "run-se.sh" wrapper script to start a GridLAB-D simulation and invoke the State Estimator tied to this simulation. For example, "./run-se.sh 13latest" would use the 13latest-config.json file in the sim_starter directory to start a simulation for the 13nodecktassets model and then invoke State Estimator on this simulation. Note that the simulation ID is printed to the terminal in the first few lines of output from "run-se.sh" and this should be copied as it will be needed for running State Forecaster.

Note that as of August 2026 the sensor-simulator service bundled with the develop platform version has two issues. These must be addressed in order to run simulations where state estimates use sensor measurements rather than simulation measurements. The first is that in the services/gridappsd-sensor-simulator/sensor_simulator.py file the feeder retrieval is not updated for multiple simulation support and needs to be changed to "feeder = opts.request['power_system_configs'][0]['Line_name']". Second, there is currently a bug in services/gridappsd-sensor-simulator/sensors/sensor.py related to sampling where the first "get_new_value" function definition should be updated to replace all lines after the first self.\_LOG.debug call with the following two lines:

````bash
new_value = value + random.gauss(0.0, self._stddev)
return new_value
````

In the third terminal from the state-forecaster directory under the state-forecaster repository, create a "logs" directory if one does not already exist. Then run "./state_forecaster.py \<simid\>" where \<simid\> is the simulation ID printed in the second terminal where the simulation and State Estimator were started. The main state_forecaster.py module spawns three subprocesses (that use Python multiprocessing support to communicate amongst themselves) and the log output for these is intermixed to the terminal where state_forecaster.py was invoked. The logs subdirectory contains separate log files for each of the three spawned subprocesses and you may wish to do "tail -f" commands for these in other terminals during the run. When State Estimator finishes producing estimates for a simulation it sends a COMPLETE processStatus message that State Forecaster receives to exit cleanly after completing any current processing.

In the current State Forecaster implementation the user must insure that the simulation "publish_period" as given in the JSON config file passed to the "run-se.sh" script matches with the TS_INCREMENT_SEC value in state-forecaster/forecast_common.py under the state-forecaster repo. Routinely used values are given in forecast_common.py with the one uncommented currently used. If the values between these two files do not match a "CADENCE MISMATCH WARNING" banner will be issued to the terminal near the beginning of the State Forecaster run and the run should be aborted. For the current application deliverable only the simulation ID is passed to State Forecaster and not the full simulation request that contains publish_period. This was done to simplify usage of State Forecaster by allowing State Estimator to start the simulation. Should State Forecaster become a GridAPPS-D platform-integrated application, the simulation request object will be passed and this can be used to automatically synchronize TS_INCREMENT_SEC with publish_period.

Finally, State Forecaster can also be run using state estimates provided in a JSONL format file (output from a previous invocation of State Estimator) rather than using streaming state estimates over the GridAPPS-D message bus. This mode is run simply by invoking "./state_forecaster.py" (no arguments) from the state-forecaster directory. See the forecast_feed.py file for the name of the state estimate JSONL file that will be used as input and also note TS_INCREMENT_SEC must match this file and FEED_RATE_HZ should be set so that training for a block completes before a new block of data has accumulated such that training does not fall behind.
